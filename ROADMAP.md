## What the rebuild fixed, and the one gap it left

Before the migration, role metadata lived in three hand-maintained places:
`index.yaml`, the `> **Version:**` line in `prompt.md`, and the same line in
`README.md`. Nothing enforced agreement and 12 roles disagreed with themselves.

Generating `index.yaml` and `dist/` from `role.md` frontmatter ended that for
two of the three copies — they are derived, and CI fails on stale artifacts.

**The per-role `README.md` is still hand-written**, per REBUILD_PLAN §3.1. That
leaves exactly one unguarded copy of every role's version and category, and it
is already drifting. The migration read its versions from the stale
`index.yaml` rather than from the prompts, which silently reverted nine roles
from 1.1 back to 1.0 and `spray` from 2.0 to 1.0 — while `spray`'s README and
its own `<MASTER_PROMPT version="2.0">` body kept saying 2.0.

The reason nothing caught it: every check in `validate-index.sh` is
*existence*-shaped ("the referenced file is present"). None was
*agreement*-shaped ("these files say the same thing"), and a hand-written copy
going stale is only ever caught by the second kind.

## Now — Close the drift class

1. **Restore the lost versions.** Nine roles to 1.1, `spray` to 2.0, sourced
   from the pre-migration prompt bodies (`73d2285` bumped 19 prompts to 1.1;
   `24525e9` bumped spray to 2.0). Done.
2. **Add an agreement check.** `validate-index.sh` now verifies each role
   `README.md` against its `role.md` frontmatter on version and category. It
   fails on `main` today with exactly the `spray` case — that is the point.
   Done.
3. **Finish the module rename.** `catalog.yaml` still declared
   `name: agent-roledefinitions-submodule` after the repository URL had already
   moved to `Agent-Roles`. Resolves open decision #2 in the rebuild plan. Done.
4. **Generate the README metadata header.** The durable fix, and a deliberate
   divergence from REBUILD_PLAN §3.1: the README is the only participant left
   in the drift, so leaving it hand-written preserves the problem the rebuild
   set out to remove. Generate the `> **Version:** … | **Category:** …` block
   from frontmatter, hand-write the prose below it, and the check above
   becomes redundant. **Not yet done** — the check is the interim guard.

## Next — REBUILD_PLAN Phase 2

Prompt modernization (§3.2) and config templating (§3.4). Order matters:

- One category per PR: engineering → utility → productivity → education →
  entertainment → **health last**.
- Config templating (§3.4) lands *before* any health rewrite, so
  `{{crisis_block}}` is injected from `config/crisis-resources.yaml` and the
  build fails closed rather than silently dropping a safety block.
- `test-roles.sh` currently emits four warnings about crisis numbers hardcoded
  outside `config/` (psy, frank, vita, agora). Templating turns those warnings
  into the thing it removes.

Before this starts, push the `v1.x` final tag REBUILD_PLAN Phase 1 calls for —
it is still outstanding, and pinned submodule consumers need it to exist
before the layout moves further.

## Later — Phases 3 and 4

Per REBUILD_PLAN §4, unchanged in substance. Two opinions carried forward:

- **Prefer two build targets to six.** `system-prompt` (the paste-and-play
  promise in PURPOSE.md) and the generated manifest (keeps `resolve.sh` and
  submodule consumers alive). REBUILD_PLAN §3.1 and §3.6 specify six plus an
  MCP server; §5 itself warns about scope creep. Add a target when a real
  consumer asks for one.
- **Behavioural evals (§3.5) come before the health-role rewrites**, not after.
  Their crisis-detection promises should be tested promises.

## Known risks

- **Don't lose the voice.** The personas' character is the product; rewrites
  are repackaging. Carried from REBUILD_PLAN §5.
- **Health roles are load-bearing.** They target vulnerable users. No health
  prompt-body change merges without a passing crisis-detection eval.
- **Existing consumers.** The generated root `index.yaml` + `resolve.sh` +
  tag-pinning contract is what keeps submodule consumers working; changes to
  it are breaking changes regardless of how the source is stored.
- **Hand-written copies of generated data are the recurring failure mode
  here.** It has now happened twice. Each time something becomes derived,
  either generate every copy of it or add an agreement check in the same PR.
